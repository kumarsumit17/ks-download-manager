# Stage 5 decisions log

Open decisions taken while building Stage 5 (Final) without stopping for the owner. Each entry: the decision, the reason, and the alternative not taken. Items left undone are marked **Not done**.

## Part 1 — Single-video downloads

- **yt-dlp build: the unpacked `yt-dlp_macos.zip`, not the single-file `yt-dlp_macos`.** The single file unpacks about 120 MB of Python to a temp folder on every run, and its unpacked libraries cannot carry our signature. Alternative: the single file (37 MB download, simpler bundling, slower start, unsignable libraries).
- **One architecture per app build, not universal.** Deno is 80 MB (arm64) / 99 MB (x86_64); a universal app would be about 430 MB. `scripts/sidecars.mjs <triple>` prepares either architecture; both were built and checked. Alternative: universal binaries via `lipo`.
- **Hashes pinned from the release's own `SHA2-256SUMS` (yt-dlp), `.sha256sum` files (Deno) and a hash taken after download (ffmpeg tarball); GPG signatures not checked.** `gpg` is not installed on this Mac and installing tools was out of scope. To do by hand when moving a pin: check yt-dlp's `SHA2-256SUMS.sig` and ffmpeg's `.asc` with the publishers' keys. Alternative: install GnuPG and check now.
- **Signing.** Tauri signs `externalBin` programs without entitlements and does not sign resources, so `scripts/sign-macos.sh` (run by `npm run bundle:mac`) signs after the build: every Mach-O in yt-dlp's folder with the hardened runtime, Deno with `com.apple.security.cs.allow-jit` only (V8 crashes with "Failed to reserve virtual memory for CodeRange" without it), ffmpeg/ffprobe plain, then re-seals the app. Measured with the ad-hoc signed hardened build: Deno without JIT crashed and yt-dlp silently fell back to fewer formats; with the entitlement, a real YouTube download (challenge solved by Deno, streams merged by ffmpeg) succeeded from inside the bundle, and the app itself starts.
- **Ad-hoc only: yt-dlp gets `disable-library-validation`.** Ad-hoc signatures have no Team ID, so library validation refused yt-dlp's own Python library ("different Team IDs"). With a Developer ID every library has the same Team ID and the exception is not used. **To check with a real certificate:** (1) yt-dlp runs without `disable-library-validation`; (2) Python's `ctypes`/`cffi` need no `allow-unsigned-executable-memory`; (3) notarisation accepts `_internal/Python.framework/Python`, a malformed framework copy in the upstream zip that `codesign` will not sign ("bundle format is ambiguous"); it is not loaded at run time (PyInstaller loads `_internal/Python`). If notarisation rejects it, delete that copy in `sign-macos.sh`. (4) Deno with `allow-jit` passes notarisation. (5) DMG creation after re-signing (Tauri builds the DMG before our re-sign, so `bundle:mac` builds the `.app` only).
- **No quiet fallback when Deno fails.** yt-dlp exits 0 with fewer formats when its JavaScript runtime fails; any `[jsc] … Error` warning now fails the lookup or download ("the JavaScript runtime did not run … Nothing was saved").
- **Stopping yt-dlp uses `/bin/kill -s TERM -- -<pgid>`, then `KILL` after 3 s,** instead of `libc::killpg` (no new direct crate and no `unsafe`). Windows uses `taskkill /T /F` (untested).
- **Update hashing and unpacking use system tools** (`/usr/bin/shasum`, `/usr/bin/ditto`; `certutil` and `tar` on Windows, untested) rather than a hashing or zip crate. Alternative: `sha2` (already in the lock file through Tauri's build tools) as a new direct dependency, which is not pre-approved.
- **The update fetch for yt-dlp uses the GitHub API** (`releases/latest`), only when the user clicks **Update video component**. That button is on a failed video's details for now; Settings gets it in Part 3.
- **Links that answer with a web page go to yt-dlp; so do links the engine gets 401/403/405/429 for.** A plain page shows "This link is a web page, not a file." Alternative: a host list of video sites (would go stale).
- **Videos get one Download button.** "Download later" is not offered for video links ("one Download action"); a paused or queued video can still be resumed later.
- **Pausing a video before any byte arrived** leaves its hidden folder in place, so it comes back as Paused (0 bytes). Harmless; resume starts it.
- **Temp folder cleanup of orphans** (a `.ksdownload-video-<id>` folder whose row was removed while the app was not running) is not done: the app only knows folders of downloads in its list. Alternative: scan every save folder at start-up.
- **Windows parts are written but untested:** process group flags, `taskkill`, `attrib +h` on the temp folder, `certutil`/`tar` in the update. Release stage.

## Part 2 — Chrome extension

- **Host mode is the app's own executable** (Chrome starts it with the extension origin as argument; it never opens a window), not a separate helper program. One program to sign and ship. Alternative: a small separate host binary.
- **YouTube button floats at the bottom right** of the window on watch and Shorts pages, instead of being inserted into YouTube's toolbar: it depends only on the page address, so YouTube layout changes cannot break it. Alternative: insert it next to Like/Share (looks native, breaks when YouTube changes its markup).
- **"youtu.be links":** a youtu.be link opens a watch page, where the button appears; links to YouTube videos on other pages get a right-click menu item ("Download video with KS Download Manager"). This needs the `contextMenus` permission (no install warning). Alternative: no link menu.
- **`activeTab` and `storage` permissions** added beyond the four in the plan: `activeTab` lets the popup see the current site only when the user opens it (no install warning); `storage` keeps the browser-downloads switch.
- **Browser downloads hand-off** pauses Chrome's download while the app checks the link, then cancels it only if the app accepted it, else resumes it. Alternative: cancel at once (loses downloads the app cannot fetch, such as signed-in ones).
- **Socket fallback path** `/tmp/ksdm-<uid>/ext.sock` (folder `0700`) when the app data path would pass the 104-byte limit. Seen in testing with a long scratch home folder.
- **Chrome API types** are a hand-written `extension/src/chrome.d.ts` instead of `@types/chrome` (not pre-approved). The extension's tests use the existing `@types/node` for `node:test`.
- **Extension build** uses the app's Vite (one IIFE bundle per script, `extension/build.mjs`); no new package.
- **Engine fix found in the real test:** a large image CDN ignored `If-Range` with its ETag and answered 200, which failed the download ("server ignored the byte range request"). The engine now drops `If-Range` for that download and checks each 206 reply's validator instead; each 200 is judged by the If-Range that request carried (a race between connections otherwise). Test added.
- **File names from addresses without an extension** (X: `…/media/<id>?format=jpg`) get one from the Content-Type (`files::name_with_type`). Written in the app for now; it is generic and moves to ks-utility with Part 4's `v0.2.0`.
- **Not fixed in Part 2, for Part 3:** tiny files get as many connections as large ones (a 9 KB image used 16), and repeated testing made Wikimedia answer 429; the adaptive connection count must start small and size connections by file size.
- **Not tested:** the extension inside Chrome (loading it unpacked needs `chrome://extensions`, which I cannot drive). Tested instead: the hand-off end to end by sending Chrome's exact framed messages to the app's host mode, with the app running (image, X original image, YouTube video, web page refused, wrong kind refused, foreign extension refused, second app copy hands over and exits); the site rules against live X images (small 59 KB → original 151 KB); unit tests for the rules and `srcset`. Placement and look of the buttons on the live sites need checking by hand.

## Part 2 review (owner, approved with changes)

- **Validators after dropping If-Range:** once a download stops sending `If-Range`, a 206 with no validator or a different one is `FileChanged` (restart once, then fail; the partial file is discarded). While `If-Range` is sent, a 206 without a validator is still accepted. Tests: matching validators complete; missing ones never produce a mixed file (new test-server option `no_validator_on_206`).
- **Dangerous browser downloads stay in Chrome:** only `danger` `safe` or `accepted` is handed over; the verdict is checked when the download appears and again after pausing it (`chrome.downloads.search`), because Chrome may flag it meanwhile. A file whose danger is only decided after it finishes (content scans) can still look `safe` at that moment: the option's description says Chrome's safety check does not apply to handed-over files. Alternative: wait for Chrome's verdict to settle (Chrome only settles it at the end of its own download, so nothing could be handed over).
- **Hindi for the extension option:** `extension/_locales/hi/messages.json` added now with the two hand-off strings (other keys fall back to English until Part 4). The Hindi wording is mine; marked for the owner's review in Part 4's `docs/hindi-review.md`.
- **Our user ID without a new crate:** std has no `geteuid`; the ID comes from `/usr/bin/id -u`, once per process. It names the fallback folder and is compared with the folder's owner. If it cannot be read, the fallback is refused. Alternative: `libc` as a direct dependency (not pre-approved).
- **The fallback folder is never repaired:** an existing `/tmp/ksdm-<uid>` that is not ours, a link, or not `0700` is refused rather than changed (before, the app set `0700` on whatever was there). The extension then reports the app as not reachable; the owner can delete the folder.
- **Silent connections:** the app closes a connection that sends no complete line (ending in a newline) within 5 s. Tested with a 200 ms limit.
- **Image button:** the `elementsFromPoint` look-up runs at most once per animation frame, with the latest pointer position.

## Part 1 review (owner, approved with changes)

- **Temp folder identity:** `ks-owner.json` marker (app, download ID, URL, creation time) in every video temp folder. A folder is continued in or removed only when its marker names that download. Otherwise a fresh `.ksdownload-video-<id>-<n>` is used and stored in the record's new `temp` field; the old folder waits for Part 3's leftover-files cleanup. The marker file is not counted as downloaded bytes.
- **IDs never reused:** `downloads.json` gains `nextId` (older lists without it still load; the next ID is never below any ID in the list).
- **Signatures checked** with GnuPG (installed with Homebrew as a development tool, owner-approved): yt-dlp `SHA2-256SUMS.sig` and ffmpeg's `.asc` both good; fingerprints and the repeat procedure in `docs/THIRD_PARTY.md`. Deno publishes no signature, only hashes.
- **Licences:** yt-dlp's `_internal/THIRD_PARTY_LICENSES.txt` is in the bundle (checked in the built app, 243 KB). Deno: `scripts/deno-notices.mjs` downloads each of the 1,048 crates.io crates in Deno's `Cargo.lock` and copies their licence files, plus V8's and ICU's licences, into `licenses/deno-THIRD-PARTY.txt` (8.5 MB). **Still missing:** 123 crates publish no licence file in their archive; for those the file lists the licence each declares (mostly Apache-2.0, MIT, or both; 15 declare none). Their texts would have to come from each crate's repository; not done. V8's and ICU's texts are taken from their `main` branches, not from the exact versions Deno 2.9.8 links. Alternative: fetch per-crate repositories.
- **Messages:** "confirm you're not a bot" and HTTP 429 → a temporary block by the site (try later or on another network), no update offered. HTTP 403 → "the site refused the download" with the update offered as one possible fix, no longer reported as "out of date".
- **Typed video names** keep their full text; only a known media extension is replaced by the real one ("Mr. Smith" → "Mr. Smith.mp4").
- **`sign-macos.sh`** counts the files it could not sign and prints the total (1 for this yt-dlp build: the malformed framework copy).
- **For Part 7:** the yt-dlp update is explicitly exempt from quarantine marking; the trade-off is written in `specs/video-playlists.md` and in `component.rs`.
