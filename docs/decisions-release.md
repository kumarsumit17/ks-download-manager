# Release decisions log

Decisions taken while building the release setup (`docs/release-plan.md`, approved 2026-11-21). Each entry: the decision, the reason, and the alternative not taken. Items left undone are marked **Not done**.

## Phase A: macOS and the extension

- **The version script edits text, not parsed JSON/TOML.** `scripts/set-version.mjs` adds `"version"` after a known key (`private` in `package.json`, `productName` in `tauri.conf.json`) and replaces the exact `0.0.0` placeholder elsewhere, so the files keep their layout and `Cargo.lock` still matches (`--locked` builds keep working). Every file is checked before any is written. Only the `ks-download-manager` entry in `Cargo.lock` changes; the internal `engine` crate keeps `0.0.0` (it is never published). Alternative: `cargo set-version` (a cargo-edit install) and `npm version` (rewrites the whole file).
- **No Chrome host manifest from `/Volumes/…` or `…/AppTranslocation/…`.** A path test, not a system call: these are the two places a first open from the DMG or from a quarantined Downloads copy runs from, and both disappear. Alternative: `SecTranslocateIsTranslocatedURL` (needs a new crate and `unsafe`).
- **Deno notices: standard texts for the 123 crates without a licence file (owner, C).** Texts come from SPDX `license-list-data` v3.29.0 (released 2026-09-16), fetched by commit `31ba1a50e5397e00a304dbadc76531740e89ee48` so they cannot change under the same name, and cached in `src-tauri/binaries/.cache/spdx/`. Each licence appears once, with the list of crates that declare it; an `X WITH Y` declaration adds both texts (Apache-2.0 and LLVM-exception). Ten texts cover all 123 crates (Apache-2.0, BSD-2-Clause, BSD-3-Clause, BSL-1.0, CC0-1.0, LGPL-2.1-or-later, LLVM-exception, MIT, Unlicense, Zlib). The notices file says twice that these come from the declared licence, not from the crate's own file, and that copyright placeholders are the template's. Correction to `docs/decisions-stage5.md` ("Part 1 review", licences): no crate in Deno 2.9.8's lock file declares nothing; all 123 declare a licence. Still open from Stage 5: V8's and ICU's texts come from their `main` branches, not the exact versions Deno links. Alternative: fetch each crate's repository for its own file (not every crate has a usable repository link, and the tag naming varies).
- **Runner images are named versions (owner, D): `macos-15`, `ubuntu-24.04`, and `windows-2025` for phase B.** Reason: a `-latest` label moves to a new OS image when GitHub decides, which changes the compiler, SDK, Xcode and preinstalled tools under an unchanged workflow, so a release could differ from the last green CI run, or break, without any commit. A named image changes only when a commit changes it, and that commit's CI run shows the effect. `macos-15` is Apple silicon (arm64), so the arm64 build is native and x86_64 is cross-compiled. Cost: GitHub retires old images on a published schedule; moving to the next one is a deliberate one-line change. Alternative: `-latest` (no upkeep, unannounced changes).
- **SHA256SUMS is written in the `attest` job, before the attestations, not in `release`.** The plan attests `SHA256SUMS` too, so it must exist first. The `release` job then re-checks every sum and runs `gh attestation verify` on every file before creating the draft. The ffmpeg source tarball is fetched in `attest` and checked against the pinned hash in `src-tauri/sidecars.json`, rather than passed on from a mac job.
- **No Apple secret is in the environment of the `tauri build` step.** Tauri's CLI signs and notarises by itself when it sees `APPLE_CERTIFICATE`, `APPLE_ID` and so on; that would sign before `scripts/sign-macos.sh` re-signs the bundled programs and send an app to Apple that is then changed. The secrets are given only to the steps that use them.
- **The Developer ID certificate goes into a temporary keychain** with a random password, deleted at the end of the job (`if: always()`); the decoded `.p12` is deleted right after import.
- **`sign-macos.sh` with a real identity removes the malformed `_internal/Python.framework` copy that `codesign` cannot sign,** instead of waiting for notarisation to reject it: Apple's notary refuses any unsigned Mach-O, and Part 1 recorded that the copy is never loaded (PyInstaller loads `_internal/Python`). Ad hoc keeps the old behaviour (left unsigned, counted). Any **other** file that cannot be signed now stops the script in both modes; before, it was only counted. **To check with the first Developer ID build:** yt-dlp still runs after the removal (hand check in `docs/release-plan.md` section 9).
- **Release notes come from `scripts/release-notes.mjs`**: the `CHANGELOG.md` section for the version, then per-platform text chosen by how the files were actually signed (each mac job records `developer-id` or `ad-hoc`; the two must agree or the job fails). The ad-hoc text gives the macOS 15 "Open Anyway" steps and the `xattr` command. The notes also say the app does not check for updates (owner, E).
- **The `version` job also requires a dated `CHANGELOG.md` section** (`## [X.Y.Z] - YYYY-MM-DD`), so a release never ships with "unreleased" notes. `CHANGELOG.md` has `## [0.1.0] - unreleased` until the owner dates it (step 0 in `docs/release.md`).
- **The extension is built on `ubuntu-24.04`**, not macOS: it is plain TypeScript and a zip, and Linux runners are cheaper and faster. Checks: the ID from the zipped manifest's key is `ikplfdbdfikcokpegkapjdedlgifmkbe`, the key equals the repository's, and the version is the tag's.
- **x86_64 programs are run under Rosetta when the runner has it;** otherwise the job prints a warning and it stays a hand check. The arm64 programs are always run.
- **README: the app does not check for updates (owner, E).** Stated with the one exception the user starts: "Update video component" fetches yt-dlp from GitHub when clicked. New versions: the GitHub Releases page.
- **The CI benchmark runs on a shared runner.** It uses only the local throttled server; its floor (500 MiB/s unthrottled) is about a sixth of this Mac's result. If shared runners prove too slow or noisy, the floor is lowered through `KSDM_BENCH_FLOOR_MIBS` in `ci.yml`, recorded here.
- **CI's unthrottled floor is 100 MiB/s (owner, 2026-11-21).** The `bench` job on `macos-15` measured 514 and 627 MiB/s, then 187, 269 and 318 MiB/s on the same engine code within the hour: runner variance, not a regression. CI now sets `KSDM_BENCH_FLOOR_MIBS=100`, which only catches a catastrophic slowdown; `bench.rs` keeps 500 as the default for local runs on the owner's Mac. Every run writes the table and the measured unthrottled speed to the job summary, so a downward trend is visible while it passes. Unchanged: the speed-up checks against the baseline, the missing-count check and the one-connection timing check (if that one fails on CI, it is reported to the owner, not widened). Only the floor was changed; no Windows test was touched.
- **Not done / not run:** neither workflow has run yet (no push from here). The Developer ID path (keychain, notarisation, stapling, `spctl`) has never run; it is written from Apple's documented tools and is checked on the first release with the secrets. Tested locally: the version script, the extension ID, the notes, the Deno notices regeneration, ad-hoc signing of a built app and `make-dmg.sh` (mounted, app and Applications link present, `codesign --verify --deep --strict` passes inside the image).

## Phase B: Windows beta

- **zlib 1.3.2, not 1.4.** 1.4 was released on 2026-11-05, two weeks before this was built; 1.3.2 (2026-02-17) is the newest release with months of use. Pinned by SHA-256 from the GitHub release; its `.asc` was checked against Mark Adler's key (`docs/THIRD_PARTY.md`). Moving to 1.4 is a later, separate change.
- **The Windows ffmpeg is cross-built with Ubuntu's `x86_64-w64-mingw32-gcc-win32`**, not the default `x86_64-w64-mingw32-gcc`, which may point to the "posix" variant and pull in winpthreads. The build fails if `ffmpeg.exe` or `ffprobe.exe` imports any DLL from the toolchain (libgcc, winpthread, zlib); only Windows' own DLLs are allowed. `-static -static-libgcc` link everything else in.
- **The GPL/non-free check runs twice:** on `config.h` in the build (every target, macOS included), because the Linux build machine cannot run the `.exe`; and as `ffmpeg.exe -buildconf` on the Windows runner.
- **Windows checks are a job of their own (`check-windows`), not a row of the `check` matrix.** It needs the cross-built ffmpeg from `ffmpeg-windows`; a matrix-wide `needs` would make the macOS row wait for, and be skipped by a failure of, a Windows-only job. The macOS job is unchanged.
- **`sidecars.mjs` unpacks with `%SystemRoot%\System32\tar.exe` by full path.** Git Bash (the shell of the Windows jobs) puts GNU tar first in `PATH`; it cannot read zip files and reads `D:` as a host name. The app itself runs `tar`, `certutil`, `reg`, `attrib`, `taskkill` by name: Rust's `Command` looks in the system folder before `PATH` on Windows, so these are always Windows' own.
- **The pipe is created in `bind()` under Tauri's own Tokio runtime** (`tauri::async_runtime::handle().inner().enter()` in `lib.rs`), so the first instance, which is the single-instance lock, exists before Tauri starts, and is then served on the same runtime. Alternative: create it with `CreateNamedPipeW` and hand the raw handle to Tokio (more `unsafe`).
- **Pipe name `\\.\pipe\com.ks.downloadmanager-<USERNAME>`.** The name only keeps users apart; security is the same-user check (owner approved `windows-sys`): the host checks the server process, the app checks each client process, by comparing the user SID of the process token with our own. All `unsafe` is in one module (`handoff.rs`, `mod win`). A pipe of our name made first by another user makes `bind()` fail: the app runs, without the extension.
- **The host opens the pipe with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`.** Without it, whoever owns the pipe could impersonate the host's user (Windows' default for a client is full impersonation). Not in the plan; found while building.
- **After answering, the app waits (up to 5 s) for the client to close the pipe before closing its own end.** Closing a Windows pipe end with an answer still in transit can drop it. The host reads one line and closes, so the wait is normally a few milliseconds.
- **The Chrome host manifest lives next to the app (`<install folder>\com.ks.downloadmanager.json`).** The installer hook does not write JSON itself (NSIS has no JSON escaping): it runs `"<app>.exe" --register-chrome-host`, which writes the file and the `HKCU` key with the same code the app runs at each start, then exits. The uninstall hook deletes both with NSIS's own commands, so a broken app cannot block it. As on macOS, registration happens only when Chrome's own folder exists (`%LOCALAPPDATA%\Google\Chrome`).
- **`reg.exe` output is read in the console code page.** An install path with non-ASCII letters may then read back as different from the wanted value; it is simply written again at each start (harmless). Writing is exact (arguments are passed as UTF-16).
- **PowerShell output is UTF-8 without BOM** (`[Console]::OutputEncoding = New-Object System.Text.UTF8Encoding $false`), and a leading BOM is stripped anyway; the picker and the clipboard also run `-STA` (the clipboard and Forms need it).
- **`explorer.exe /select,"<path>"` is passed as a raw argument.** Rust would quote the whole `/select,…` argument when the path has a space, and Explorer does not understand that form. A Windows path cannot contain `"`. The shared "path is one argument" test uses a Windows path without `"` on Windows (it cannot exist there) and allows the closing quote; Windows also has its own exact test.
- **`taskkill` exit code 128 ("not found") counts as stopped,** since the process had already exited; any other failure is logged.
- **The installer is tested in CI** (`installer-windows`, `scripts/test-windows-installer.sh`): silent install into the runner's user account, the files, licence texts and programs it put there, the manifest and registry key from the hook; silent uninstall, then the app, manifest and key are gone. The release job runs the same script on the exact file it uploads. Not in the plan's test list; it covers the plan's installer hooks (section 4.2), which otherwise would first run at tag time.
- **The release's Windows jobs are behind one switch,** `windows` in the `version` job's outputs (`"off"` or `"on"`). Off, they are skipped and `attest` and `release` still run for macOS and the extension; on, a Windows failure stops the release.
- **LF in every checkout (owner, 2026-11-21).** The Windows runner checked the repository out with CRLF (Git's `core.autocrlf` on Windows), and `set-version.mjs` matched `\nversion = "0.0.0"\n` exactly. Fixed at the cause with `.gitattributes` (`* text=auto eol=lf`, png/ico/icns binary; `git add --renormalize .` changed no file), and in the scripts as well, so a checkout made before the attribute existed still works: `set-version.mjs` keeps each file's own line ends (test with CRLF input), `release-notes.mjs` splits CHANGELOG sections on `\r?\n` (test with CRLF input), and the release workflow's dated-section check strips `\r` before `grep …$`. Also found while looking: `deno-notices.mjs` read Windows `tar` listings (CRLF) and split a Windows path on `/` (both fixed earlier in phase B). Checked and not affected: the other scripts (they only parse JSON or write text), the UI and extension tests (no file reads), and the Rust tests (`lines()`, JSON, or exact bytes the test wrote itself).
